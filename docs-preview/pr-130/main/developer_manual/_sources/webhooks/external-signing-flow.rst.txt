=======================================
External signing with native webhooks
=======================================

This guide follows an **existing external application** that keeps its own
interface and authentication. It creates a LibreSign signing request for
a person **without a Nextcloud account**, controls the invitation, receives
a signed-workflow event, then retrieves the final PDF with authorization.

**Scope:** LibreSign ``main`` (16.0.0-dev), Nextcloud 36, and the native
``webhook_listeners`` app. This is development behavior, **not a stable
LibreSign 16 announcement**. Stable LibreSign 13–15 do not expose this
aggregate event; retain their version-specific documented integrations.

.. important::

   The native webhook is not a drop-in replacement for the old
   per-request ``callback``: it sends a **JSON event**, not a multipart PDF,
   and its destination is registered administratively in Nextcloud.
   In the unmerged removal PR LibreSign/libresign#9426, ``callback``
   in a signing-request payload is rejected with HTTP 422, and the
   global ``webhook_sign_url`` fallback is removed. Existing installs
   may retain that legacy behavior until upgrading. Stored callback URLs are not migrated
   into Webhook Listeners subscriptions. Migrate existing consumers
   *before* upgrading their integration.

1. Prepare the Nextcloud environment
------------------------------------

Install compatible Nextcloud 36 and LibreSign development builds. Enable
Webhook Listeners and configure Nextcloud's **Cron** background jobs. Ensure
the server can reach the receiver over HTTPS and can deliver e-mail.

In the Nextcloud container, for example:

.. code-block:: console

   sudo -u www-data php occ app:enable webhook_listeners
   sudo -u www-data php occ background:cron

Use an SMTP test server, such as Mailpit, for disposable tests. Use a
dedicated integration Nextcloud account with an App Password and the
permissions needed to create requests and read only its own PDFs.

2. Register the native completion event
---------------------------------------

An authorized **Nextcloud administrator** registers a webhook subscription
using Webhook Listeners' own OCS API, not LibreSign's signing API.

.. code-block:: bash

   export NC_URL="https://cloud.example.test"
   export NC_ADMIN="nextcloud-admin"
   export NC_ADMIN_APP_PASSWORD="<from-secret-manager>"
   export RECEIVER_URL="https://integrator.example.test/webhooks/libresign"
   export RECEIVER_SECRET="<random-per-receiver-secret>"

   curl --fail-with-body -sS \
     -u "$NC_ADMIN:$NC_ADMIN_APP_PASSWORD" \
     -H "OCS-APIRequest: true" \
     -H "Accept: application/json" \
     --data-urlencode "httpMethod=POST" \
     --data-urlencode "uri=$RECEIVER_URL" \
     --data-urlencode 'event=OCA\Libresign\Events\SigningRequestCompletedEvent' \
     --data-urlencode "authMethod=header" \
     --data-urlencode "authData[X-LibreSign-QA-Token]=$RECEIVER_SECRET" \
     "$NC_URL/ocs/v2.php/apps/webhook_listeners/api/v1/webhooks"

Inspect both HTTP status and ``ocs.meta.statuscode``. The receiver must
reject requests without the expected secret. Leave ``userIdFilter`` unset
for external signers, because the incoming wrapper's ``user`` can be null.
Exact administrative fields and authentication modes depend on the installed
Nextcloud Webhook Listeners version; see :doc:`configuration`.

3. Create the request without an initial invitation
---------------------------------------------------

Authenticate as the **integration requester**, not the signer. Prepare a
base64-encoded PDF and replace the sample ``<BASE64_PDF_BYTES>`` value.
The signer's e-mail is an identity method, not a Nextcloud username.

.. code-block:: bash

   export NC_USER="integration-account"
   export NC_APP_PASSWORD="<from-secret-manager>"
   export API="$NC_URL/ocs/v2.php/apps/libresign/api/v1"

   curl --fail-with-body -sS \
     -u "$NC_USER:$NC_APP_PASSWORD" \
     -H "OCS-APIRequest: true" \
     -H "Content-Type: application/json" \
     -H "Accept: application/json" \
     -d '{
       "name": "External contract",
       "file": {"name": "contract.pdf", "base64": "<BASE64_PDF_BYTES>"},
       "status": 1,
       "signers": [{
         "displayName": "External signer",
         "notify": 0,
         "identifyMethods": [{
           "method": "email",
           "value": "signer@example.test",
           "requirement": "required"
         }]
       }]
     }' \
     "$API/request-signature"

Capture the returned file ``id`` and workflow ``uuid``. Confirm the
request is ``Able to sign`` (status 1) before inviting anyone. A valid
creation response does not prove any e-mail was sent. In the disposable
test ``notify: 0`` sent **zero** initial invitations.

4. Send the invitation explicitly
---------------------------------

Send it using LibreSign's authenticated endpoint:

.. code-block:: bash

   export FILE_ID="123"  # replace with the returned request ID

   curl --fail-with-body -sS \
     -u "$NC_USER:$NC_APP_PASSWORD" \
     -H "OCS-APIRequest: true" \
     -H "Content-Type: application/json" \
     -d '{"fileId":123,"signers":[{"email":"signer@example.test"}]}' \
     "$API/notify/signers"

Replace the example numeric ID in the JSON. This endpoint lets **LibreSign**
send the correct signer invitation; it does not provide a generic contract
for extracting or constructing a secret signing URL. In the tested
environment, one explicit notification produced **one** Mailpit message.
Check mail-server delivery rather than treating HTTP 200 as receipt.

5. Sign without a Nextcloud session
-----------------------------------

Open the invitation URL in a fresh browser profile **without Nextcloud
authentication**. Complete the signing method allowed by the installed
policy. The tested development run used ``clickToSign`` and received
HTTP 200 from the signing endpoint. Email-token signing may require a
separate verification e-mail; the authentication policy decides the steps.

For multiple signers, the first signature may leave the document
``Partially signed``. That state is **not** a completion event. For an
envelope, wait for the parent envelope workflow to complete, not merely
one child PDF.

6. Receive, authenticate and correlate the event
------------------------------------------------

Nextcloud queues a ``WebhookCall`` background job. Cron performs an
asynchronous HTTP POST; the event is **not delivered synchronously** by
the signing endpoint. The receiver verifies the configured header, parses
the JSON body, and checks:

- ``event.class`` equals
  ``OCA\Libresign\Events\SigningRequestCompletedEvent``.
- ``event.contractVersion`` equals ``1``.
- ``event.status`` equals ``completed``.
- ``event.requestUuid`` maps to a request controlled by this integrator.
- ``event.eventId`` has not already been processed successfully.

For the JSON shape, including ``requestType`` (``document`` or
``envelope``) and an optional null ``user``, see
:doc:`signing_completion`. Persist the event ID and return a 2xx when
accepted. Do not expect exactly-once delivery, guaranteed ordering, or
automatic retries; run periodic, bounded reconciliation independently.

7. Recover and validate the signed document
-------------------------------------------

The event does not contain the PDF or authorize its download.
Using the **requesting account's** credentials, reconcile the current
state and determine the actual authorized file path:

.. code-block:: bash

   curl --fail-with-body -sS \
     -u "$NC_USER:$NC_APP_PASSWORD" \
     -H "OCS-APIRequest: true" \
     -H "Accept: application/json" \
     "$API/file/list?details=1&fileIds%5B%5D=$FILE_ID"

Check the intended entry's ``status``, ``uuid`` and file/envelope
membership. Resolve the final signed file through the authorized account's
file listing. **Never derive a WebDAV path from the webhook UUID.**

.. code-block:: bash

   export SIGNED_DAV_URL="https://cloud.example.test/remote.php/dav/files/integration-account/Contracts/contract.signed.pdf"

   curl --fail-with-body -sS \
     -u "$NC_USER:$NC_APP_PASSWORD" \
     -o signed-contract.pdf "$SIGNED_DAV_URL"

   pdfsig signed-contract.pdf

The path above is **illustrative**; use the actual authorized path in
your installation. Check the PDF signature's cryptographic validity,
coverage and trust chain separately. The disposable QA validated a
signed PDF with SHA-256/PKCS#7; its test CA was not trusted by the host.
An unrelated authenticated user got HTTP 404, and anonymous access
received HTTP 401 for that file. Keep negative permission checks in
integration tests.

8. Handle envelopes and non-completion states
---------------------------------------------

The tested two-file envelope remained Draft immediately after
``POST /request-signature`` despite a requested status 1. An authorized
``PATCH /request-signature`` with envelope ``uuid`` and ``status: 1``
made it ready for signing. Check the actual response before notifying.
The completed envelope generated one event with
``requestType: "envelope"``.

With rejection policy ``cancel``, an external rejection ended the
workflow in ``Canceled`` (status 6) and sent **no completion event**.
A system requiring cancellation alerts must use separate supported
events if available, or authenticated polling; the completion event alone
cannot report a cancellation or every individual signing step.

Migration checklist
-------------------

1. Record the callback destinations and downstream consumers in the
   existing integration; update their endpoints to consume JSON rather
   than receiving PDF multipart bodies.
2. Register the native event subscription and secure the receiver.
   There is no automatic conversion of stored callback URLs to
   subscriptions, and no direct per-request webhook destination.
3. Replace the old ``callback`` request parameter and stop using
   ``webhook_sign_url``. Verify that legacy input produces HTTP 422
   on this development line rather than silently losing a notification.
4. Join the event's ``requestUuid`` to a request created by the
   integrator. Reconcile status and fetch the PDF with its authorized
   Nextcloud identity.
5. Test initial e-mail suppression, external browser signing, delivery
   through Cron, duplicate ``eventId`` processing and authorization
   denials before changing any production integration.

Do not apply these changes to stable LibreSign 13, 14, or 15 based only
on their Nextcloud version. Use their documented OpenAPI contracts and
retain supported legacy behavior until an upgrade is explicitly planned.
